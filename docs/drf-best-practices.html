API engineering guide

Django REST Framework best practices

Good API design is more than adding serializers and viewsets. A maintainable Django REST Framework (DRF) API makes access rules explicit, validates input at the boundary, keeps database work predictable, and tests the behavior clients depend on. Use this checklist as a starting point and adapt it to your application's requirements.

1. Keep each layer focused

Use views or viewsets to coordinate HTTP behavior, serializers to validate and represent data, and models for persistence and domain constraints. Move multi-step business workflows into service functions when doing so makes them easier to reuse or test. Put complex reusable read queries in selectors or dedicated queryset methods.

Do not create a service or selector for every single line of code. Simple logic can stay close to the view or model when that is clearer. See the architecture overview for the conventions used by this template.

2. Make permissions explicit

Authentication answers who a caller is; permissions answer what that caller may do. Configure deliberate default permission classes and set object-level checks where access depends on ownership or another relationship. Do not assume that hiding a button in a frontend protects an endpoint.

For list endpoints, filter the queryset so users only receive records they are allowed to see. Object permissions alone do not automatically remove unauthorized objects from every list response. Test both detail and list access paths.

3. Validate input with serializers

Use serializers to define accepted fields, types, required values, and cross-field validation. Prefer explicit writable fields over exposing every model field by default. Keep read-only fields such as ownership, server-generated timestamps, and other trusted values under server control.

When creating or updating related objects, validate that referenced objects are available to the current user where applicable. Return clear validation errors without exposing secrets, internal stack traces, or sensitive implementation details.

4. Make querysets safe and efficient

Start from a queryset constrained to the caller's access scope. Apply filtering and ordering deliberately, and avoid allowing arbitrary client input to become raw ORM expressions or SQL fragments.

  • Use select_related() for appropriate single-valued foreign-key and one-to-one relationships.
  • Use prefetch_related() for appropriate many-to-many and reverse relationships.
  • Use pagination for potentially large collections.
  • Inspect query counts and profile slow endpoints before optimizing.

These practices help prevent N+1 query patterns, but the right loading strategy depends on the response shape and data volume.

5. Define stable API behavior

Choose a consistent response format, status-code policy, filtering behavior, and pagination style. Document which fields are nullable, which values are writable, and how clients should handle validation errors. Avoid changing the meaning or type of an existing response field without considering compatibility.

If the API is consumed by other teams or public clients, plan versioning and deprecation before making breaking changes. Generate and review an OpenAPI schema so the published contract matches the implemented endpoints.

6. Test authorization and edge cases

Test more than the successful request. Include unauthenticated requests, authenticated users with insufficient permissions, attempts to access another user's objects, invalid payloads, missing related records, empty results, and pagination boundaries.

DRF's APIClient and APITestCase can help exercise endpoints at the HTTP layer. Keep unit tests for isolated business rules and integration tests for behavior involving the database or other components.

7. Review production security settings

  • Use HTTPS and secure cookie settings appropriate to your deployment.
  • Keep secret keys, database credentials, and signing secrets out of source control.
  • Set allowed hosts, CORS, and CSRF trusted origins deliberately for the deployed environment.
  • Choose authentication and token lifetimes based on the application's threat model.
  • Apply throttling where it helps manage ordinary client usage, but do not treat application throttling as a complete denial-of-service defense.
  • Keep Django, DRF, and dependencies updated, and review security advisories.

Before shipping an endpoint

  • Is the queryset restricted to records the caller may access?
  • Are permissions explicit for list, create, update, and delete operations?
  • Are writable serializer fields intentionally selected?
  • Are large result sets paginated?
  • Have query performance and N+1 behavior been checked?
  • Are success, validation, and authorization cases covered by tests?
  • Does the API schema describe the actual behavior?
